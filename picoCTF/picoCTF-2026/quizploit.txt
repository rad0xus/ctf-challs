An NX (No-Execute) enabled binary is a compiled program that uses processor hardware features to block code from running inside memory regions meant strictly for data (such as the stack or heap).


How It Works

• Write XOR Execute (\(\text{W} \oplus \text{X}\)): Memory pages are designated as either writable or executable, never both at the same time.
• Hardware Enforcement: The CPU checks a special bit in the page table (known as the NX bit on AMD/x86, XD bit on Intel, or XN on ARM).
• Crash on Violation: If an attacker tries to inject and execute malicious shellcode inside a data buffer (like during a buffer overflow attack), the CPU triggers a protection fault and terminates the program instead of running the code.

The primary exploitation technique used to bypass the NX (No-Execute) or DEP (Data Execution Prevention) protection is Return-Oriented Programming (ROP).
Because NX marks data segments (like the stack and heap) as non-executable to prevent shellcode from running directly, attackers rely on code-reuse primitives to execute code that is already marked as executable within the binary or its loaded libraries.


Common NX Bypass Variations

• Return-to-libc (ret2libc): Redirects the execution flow to existing functions inside standard C libraries (like system() or execve()) using arguments controlled by the attacker.
• ret2syscall: Chains small code fragments together to set up CPU registers and execute a direct kernel system call (such as sys_execve).
• Memory Protection Relaxation: Uses ROP chains to call functions like mprotect() or VirtualProtect() to change the permissions of a memory page (e.g., the stack) from readable/writable to executable, effectively turning NX off for that region so standard shellcode can run.
